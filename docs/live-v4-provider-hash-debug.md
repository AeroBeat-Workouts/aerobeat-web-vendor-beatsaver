# Live BeatSaver v4 Provider Hash Mismatch Debug Record

## Exact Observed Failure

Derrick selected and imported a random live BeatSaver map on the phone and saw:

> BeatSaver map-content hash does not match selected provider version

The exception originates in `src/service.js` during `AeroBeatSaverVendorService.acquireVersion()` after archive download and inspection. The vendor compares its locally computed `sourceHash` with the selected BeatSaver version hash and throws `BeatSaverVendorError("integrity", ...)` when they differ.

A live command-line reproduction against the current BeatSaver API immediately reproduced the same failure for latest map `53F26`:

- provider version hash: `addd9d6f8e7340ad6f5633947136d8475a7a99b5`
- current AeroBeat source hash: `ac8867b62269dfdcc0483fe4f662adcb6976fa8a`
- downloaded archive SHA-1: `016c58e6b888465256762f41f3d598509c19bf0e`
- source format: v4

The selected download URL itself is keyed by the provider hash, so this is not evidence that assembly chose a different version URL.

## Expected Behavior

For provider downloads, AeroBeat must reproduce the exact hash generated by BeatSaver for the selected version. A genuine provider/archive mismatch must remain an integrity error; compatible current v4 maps must not be rejected because AeroBeat uses an older or incomplete hash-input model.

## Execution Path

1. Assembly handles `beatsaver-import` and calls `importBeatSaverById(mapId, versionHash, ...)`.
2. The service graph fetches normalized BeatSaver map/version metadata.
3. `AeroBeatSaverVendorService.acquireVersion()` selects the requested version and downloads `version.downloadUrl`.
4. `inspectBeatSaverArchive()` validates ZIP structure/CRC/limits and builds a source manifest.
5. `buildSourceManifest()` currently constructs `hashInputPaths` by iterating v2/v3/v4 difficulty metadata.
6. For each v4 difficulty, it appends `beatmapDataFilename` and `lightshowDataFilename` but deduplicates paths globally.
7. `computeBeatSaverMapHash()` hashes raw `Info.dat` followed by those deduplicated paths.
8. `acquireVersion()` compares that result to `version.hash` and throws the observed integrity error.

For live map `53F26`, v4 metadata references:

- `audio.audioDataFilename`: `AudioData.dat`
- Lightshow/Easy: `EasyLightshow.dat`, shared `Lightshow.dat`
- Standard/ExpertPlus: `ExpertPlusStandard.dat`, shared `Lightshow.dat`

Current AeroBeat hashes:

```text
Info.dat + EasyLightshow.dat + Lightshow.dat + ExpertPlusStandard.dat
```

BeatSaver's current v4 upload path hashes:

```text
canonical Info.dat + AudioData.dat + EasyLightshow.dat + Lightshow.dat + ExpertPlusStandard.dat + Lightshow.dat
```

The second sequence reproduces the provider hash exactly: `addd9d6f8e7340ad6f5633947136d8475a7a99b5`.

## Most Likely Root Cause

The v4 provider hash model is incomplete in `archive.js`:

1. It omits `audio.audioDataFilename` from v4 hash inputs.
2. It deduplicates shared `lightshowDataFilename` references, while BeatSaver writes each difficulty's referenced bytes into the hash stream in metadata traversal order.

Both differences are required to explain the live mismatch. Adding only `AudioData.dat` produced `151faa3f...`, not the provider hash. Adding AudioData and retaining the repeated shared lightshow produced the exact provider hash.

Current BeatSaver source supports this causal chain:

- [`beatsaver-main` upload validation](https://github.com/beatmaps-io/beatsaver-main/blob/master/src/jvmMain/kotlin/io/beatmaps/controllers/upload/zip.kt) writes canonical Info bytes to SHA-1 and then writes `info.toHash`.
- [`beatsaver-common-mp` v4 schema](https://github.com/beatmaps-io/beatsaver-common-mp/blob/master/src/jvmMain/kotlin/io/beatmaps/common/beatsaber/info/infoSchema4.kt) writes `audioDataFilename` bytes into `toHash`, then writes each difficulty's beatmap/lightshow bytes as validation traverses the metadata.
- [`ExtractedInfo`](https://github.com/beatmaps-io/beatsaver-common-mp/blob/master/src/jvmMain/kotlin/io/beatmaps/common/zip/ExtractedInfo.kt) owns the ordered `toHash` stream and SHA-1 digest.

## Alternative Hypotheses

1. **BeatSaver CDN returned bytes for a different version** — unlikely. The URL is keyed by the expected hash, and locally reproducing BeatSaver's v4 input sequence yields the expected hash from those exact bytes.
2. **Assembly selected the wrong version** — contradicted by the normalized map having one version and its download URL/hash matching the expected provider metadata.
3. **Raw ZIP SHA-1 should be compared instead** — contradicted by the archive SHA-1 differing from both hashes and by BeatSaver's source-hash algorithm.
4. **Path case or ZIP decompression changed bytes** — contradicted by exact provider-hash reproduction from `readEntry()` bytes.
5. **Info serialization differs** — possible for other maps if BeatSaver rewrites legacy metadata, but not causal for this reproduction because the downloaded Info bytes plus the correct ordered v4 inputs reproduce the provider hash exactly.

## Why Previous Fixes Failed

No fix has yet been attempted for this physical failure. Existing tests used deterministic synthetic archives whose expected hashes were generated by AeroBeat's own `computeBeatSaverMapHash()`. That made the implementation and fixtures agree with each other while failing to cross-check the current BeatSaver v4 algorithm. Earlier Task 12 live-map metadata checks did not acquire and verify a current v4 archive through this exact provider path.

## Unknowns

- The exact map Derrick selected is not known. The independent live reproduction proves the same error class on current map `53F26`.
- BeatSaver's canonical Info rewrite could matter for unusual/older uploaded archives; current downloaded v4 Info reproduced exactly without additional canonicalization.
- v4.1 or later may add more hash-stream inputs. A live/provider golden matrix should detect future drift.

   `Info.dat`, `AudioData.dat`, `EasyLightshow.dat`, `Lightshow.dat`, `ExpertPlusStandard.dat`, `Lightshow.dat`.

Legacy v2/v3 synthetic fixtures do not reproduce because they have no v4 audio-data or split/shared lightshow references.

## Proposed Verification

Before changing runtime behavior, add an independent v4 fixture whose provider hash is hard-coded from BeatSaver's algorithm—not computed by the implementation under test. It must include:

- `AudioData.dat`;
- at least two difficulties;
- a shared repeated lightshow reference;
- exact metadata order;
- one Standard playable difficulty.

Assert:

1. the pre-fix algorithm fails the golden expected hash;
2. manifest hash input order includes AudioData first and repeated shared lightshow occurrences;
3. the corrected algorithm equals the hard-coded provider hash;
4. changing any hashed byte produces integrity failure;
5. v2/v3 golden hashes remain unchanged;
6. live `53F26` acquisition succeeds when network evidence is available, but repo gates do not depend on live availability.

## Recommended Fix

Model provider hash inputs as an ordered sequence that may contain duplicates rather than a deduplicated set.

- For v4, prepend `audio.audioDataFilename` after Info and before difficulty payload bytes.
- For every v4 difficulty in metadata order, append its beatmap data and lightshow data paths exactly as referenced, including repeated shared paths.
- Preserve current v2/v3 difficulty traversal semantics.
- Keep archive inspection/path/CRC limits and the final strict provider comparison unchanged.
- Document the version-aware provider-hash contract and add independent golden/live regression coverage.

The source manifest may need a clearer field name than `hashInputPaths` or explicit documentation that entries are ordered and duplicates are significant.

## Implemented Verification

The repair keeps `hashInputPaths` for manifest compatibility and now defines it explicitly as an ordered, duplicate-preserving sequence rather than a set. v4 prepends `audio.audioDataFilename` and retains every beatmap/lightshow occurrence; the legacy v2/v3 branch preserves its previous sequence and deduplication behavior. Archive validation, CRC checks, limits, and the strict `expectedHash === sourceHash` provider comparison are unchanged.

Offline coverage uses an independently hard-coded v4 golden SHA-1 `96e68173fffd6454bfb38740acaf58653da11320` with raw Info bytes, AudioData, two metadata-ordered difficulties, and one repeated shared lightshow. It also proves AudioData tampering fails strict provider integrity and locks the unchanged v2/v3 source hashes `f8ed950c666baf9148a18e5f3b9731b3f2f23cb0` and `f40cee1a11222c29ccdabb3193c83b9d25a837a4`.

The optional network script `npm run test:live-v4-hash` fetched current map `53F26` and reproduced `addd9d6f8e7340ad6f5633947136d8475a7a99b5` exactly. Normal validation does not invoke that script or depend on network access.
